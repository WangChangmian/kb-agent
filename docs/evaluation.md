# 评估报告（kb-agent）

> 本文档是项目的**质量证据**：怎么建评估集、指标怎么定义、调参为什么有效。
> 相关代码：`eval/eval_set.json`、`eval/judge.py`、`eval/run_eval.py`；测试：`tests/test_judge.py`。

---

## 1. 为什么要评估

**没有指标，效果只是感觉。** 评估解决三个问题：

| 问题 | 评估如何回答 |
|------|-------------|
| 系统现在到底行不行？ | 用统一的评估集量化分数 |
| 我这次改动是变好还是变坏？ | 同一份评估集前后对比 |
| 问题出在检索还是生成？ | 分开统计"检索命中率"与"端到端准确率" |

> 实战验证：迁移到新项目后，**评估集立刻抓出一个回归**（`ask()` 里硬编码了查询词，导致只有年假类问题答对）——没有评估，这个 bug 会潜伏到演示时才暴露。

---

## 2. 评估集设计

**规模**：10 条 = 9 条知识问答 + 1 条防幻觉刁难题。

**结构**（`eval/eval_set.json`）：

```json
[
  {"question": "年假满一年可以休几天？", "answer_hint": "5 天", "section": "年假制度", "not_found": false},
  {"question": "工作日加班费按几倍工资计算？", "answer_hint": "1.5 倍", "section": "加班与调休", "not_found": false},
  {"question": "公司食堂在哪里？", "answer_hint": "未找到", "section": "无", "not_found": true}
]
```

| 字段 | 作用 |
|------|------|
| `question` | 提问 |
| `answer_hint` | 期望答案中的**关键信息**（用于判卷） |
| `not_found` | 是否为**刁难题**（知识库中不存在答案） |

**刁难题的设计意图**：验证"知识库没有的内容，模型是否会编造"。期望行为是**明确回答"未找到"**——这是防幻觉能力的直接检验。

**覆盖范围**：年假制度、加班计算、报销流程、远程办公、培训补贴（均为知识库中的硬性规定，答案可唯一确定）。

---

## 3. 指标定义

| 指标 | 定义 | 衡量什么 |
|------|------|---------|
| **检索命中率 Recall@4** | 期望关键词是否出现在检索命中的 top-4 段落中 | **检索质量**（该找到的有没有找到） |
| **端到端准确率** | 最终回答是否包含期望答案（刁难题则要求出现"未找到"） | **生成质量**（最终有没有答对） |

**判卷口径**（`eval/judge.py` 中的纯函数）：

```python
def normalize(text: str) -> str:
    """归一化：去掉所有空格，避免 '5 天' vs '5天' 的误判。"""
    return text.replace(" ", "").replace("\u3000", "")

def check_answer(answer: str, hint: str, not_found: bool = False) -> bool:
    if not_found:
        return "未找到" in answer          # 刁难题：必须明说没有
    return normalize(hint) in normalize(answer)
```

**为什么判卷要单独抽成纯函数**：① 可被单元测试覆盖（`tests/test_judge.py`）② 检索与生成共用同一套判卷口径。

---

## 4. 结果（两种向量库后端对比）

同一份评估集、同一套判卷逻辑，分别在两种向量库上运行：

| 向量库后端 | 检索命中率 Recall@4 | 端到端准确率 |
|-----------|-------------------|-------------|
| Chroma（本地单文件库） | 90% | **100%** |
| **Milvus 2.5.4**（Docker 三件套） | 90% | **100%** |

**结论**：切换向量库后端（Chroma → Milvus）**指标完全一致**，且上层业务代码（`ingest` / `retriever` / `app`）**一行未改**——验证了分层封装（`services/vector_store.py` 为唯一创建点）与配置驱动（`VECTOR_BACKEND`）的有效性。

**关于 90% 的检索命中率**：唯一未命中项是刁难题"公司食堂在哪里？"——该题在评估规则中期望"检索不到"，但由于当前知识库规模较小，任何问题都会检索到块。**关键行为（回答"未找到"、不编造）是正确的**，规则本身可后续优化（如按相关度阈值判定是否视为命中）。

## 5. 调参记录（评估驱动开发）

| 阶段 | 端到端准确率 | 动作 | 原因分析 |
|------|------------|------|---------|
| ① 基线 | 20% (2/10) | 建评估集，跑第一版 | 发现大量"检索✓ 回答✗"与"检索✗ 回答✗" |
| ② 修正判卷 | 40% (4/10) | 判卷加**空格归一化** | 两条"冤枉"失败：模型答 `5天`、标准答案写 `5 天` |
| ③ 调阈值 | **100% (10/10)** | `RETRIEVER_SCORE_THRESHOLD` 0.3 → 0.2（改在 **`.env`**） | 回答"只有标题没有内容"→ 答案所在块被阈值过滤 → 降低阈值恢复召回 |

**过程中的关键教训**：

1. **先分清"系统问题"和"判卷问题"**——20% 的分数里有一半是判卷误判（空格），修掉才看到真实的检索短板。
2. **配置要改对地方**：先改了 `config.py` 的默认值没生效——因为 **`.env` 优先级更高**（环境变量 > 代码默认值）。
3. **一次只改一个变量**，并用同一份评估集对比。

**其他可用的召回优化手段**（本项目未全部启用，作为后续方向）：调大 `top_k`、优化分块策略（按标题结构切分）、更换更强的 embedding、引入 **rerank 精排**（粗召回 top_k=16 → 精排取 top3）。

---

## 6. 方法论沉淀

1. **评估集要包含刁难题**——否则测不出幻觉
2. **判卷口径要宽容**（空格、大小写、中英文标点）——否则指标被误判污染
3. **控制变量**：评估集固定不变，一次只改一个参数
4. **记录对比**：每次调参都记录"改了什么 → 分数从多少变到多少"
5. **每个修过的 bug 补一条测试**（bug-driven testing）——判卷逻辑的 5 个用例就是这么来的
6. **评估集也是一种回归测试**：迁移、换库、改 Prompt 后都应重跑

---

## 7. 局限与后续计划

| 局限 | 影响 | 计划 |
|------|------|------|
| 评估集仅 10 条 | 覆盖不足，易过拟合 | 扩充到 50+ 条，覆盖更多文档类型与提问方式 |
| 判卷靠关键词匹配 | 无法衡量"回答质量"（是否通顺、是否答全） | 引入 **RAGAS** 指标（faithfulness / answer relevancy）或 **LLM 判官** |
| 刁难题的检索判定规则过严 | 小知识库下必然"未命中" | 改为"按阈值判定是否视为有效命中" |
| 未做检索与生成的消融实验 | 无法精确归因 | 增加"仅检索"与"仅生成"的分项统计 |
| 未测性能（延迟/并发） | 不知道生产表现 | 增加 P95 延迟、首 token 时间（TTFT）与并发压测 |

## 8. 复现方式

```bash

python eval/run_eval.py --basic     # 输出检索命中率与端到端准确率
python eval/run_eval.py --show      # 打印每条问题的检索命中内容，人工检查
```
