## 一、30 秒项目介绍（开场背熟）

> "我做了一个**企业知识库问答 Agent**：把公司文档分块、向量化存进向量库（**Milvus**，Docker 三件套部署）；用户提问时先检索最相关的段落，再让大模型**只依据这些段落**流式生成回答并**附带引用来源**。
> 另外通过 **Function Calling** 接了员工数据查询工具和"知识库检索"工具，能回答『我的年假还剩几天』这类需要查私有数据的问题。
> **亮点**是：SSE 流式打字机、防幻觉约束（知识库没有的会明说）、以及**用评估集量化调参**（10 条评估从 20% 调到 100%，并在 Chroma 与 Milvus 两种向量库上验证指标一致）。技术栈是 FastAPI + LangChain + Milvus + Docker。"

## 二、3 分钟架构讲解（对着 `docs/architecture.md` 的图讲）

1. **分层**：接口层 `app/main.py`（只管 HTTP）→ 业务层 `services/`（检索 / 生成 / Agent）→ 工具层 `tools/` → 配置层 `config.py`。
   **价值**：换向量库只改一个文件（实测：Chroma → Milvus，上层零改动）；换模型只改 `.env`。
2. **三条数据流**：
   - **入库（离线）**：文档 → 分块(500/50) → Embedding(bge-m3) → 向量库
   - **问答（在线）**：问题 → 检索 top_k=4 → 阈值过滤(0.2) → 拼 Prompt → 流式生成 → 推引用来源
   - **Agent**：模型决策调工具 → 代码执行 → 结果回填 → 循环至最终答案（带循环上限与失败熔断）
3. **向量库选型**：开发用 Chroma（零部署），生产用 **Milvus**（etcd 存元数据 + MinIO 存对象 + Milvus 引擎，支持高并发与分布式扩展），两者用 `VECTOR_BACKEND` 一行配置切换。
4. **模型选型**：对话用 DeepSeek（国内直连、支持 Function Calling）；Embedding 用硅基流动 bge-m3（**DeepSeek 没有 embeddings 接口**，chat 与 embedding 分开选型是行业常规做法）。
5. **质量保障**：10 条评估集（含防幻觉刁难题）+ pytest 单元测试（8 个用例）。

## 三、高频 Q&A（十题，背熟）

**Q1 为什么用 RAG 而不是微调？**
RAG 不改模型，改"喂给模型的内容"：知识更新只需重新入库（几分钟）、成本低、**有引用来源可追溯**；微调要改模型参数：成本高、更新慢、不可追溯，适合塑造"行为/风格"。我的场景是知识频繁更新的企业知识库，且回答要可追溯，所以选 RAG。

**Q2 RAG 的完整链路？**
入库阶段：加载 → 清洗 → 分块 → 向量化 → 写库；问答阶段：问题向量化 → 相似度检索 top_k → 相关度阈值过滤 → 拼 Prompt → LLM 生成 → 引用来源。**两阶段分离**是关键设计。

**Q3 chunk_size 怎么定？太大太小有什么问题？**
块太大：噪声多、费 token、回答发散；块太小：语义不完整、召回率低；overlap 防止语义被切断。我项目里 500/50 起步，并用评估集验证效果；进阶可按文档结构切（标题/章节）。

**Q4 召回率低怎么排查和优化？**
先用评估集定位：① 建评估集量化指标 ② 排除判卷误判（如 `'5 天'` vs `'5天'` 的空格问题）③ 看症状——回答"只有标题没有内容"说明答案所在块被阈值过滤 ④ 调参：阈值 0.3→0.2，指标 40% → 100%。其他手段：调大 top_k、优化分块、换 embedding、加 rerank 精排。**一次只改一个变量，用数据说话。**

**Q5 怎么防止幻觉？**
四层：① Prompt 写死"只依据参考资料，没有就明说" ② 相关度阈值过滤无关段落 ③ 回答带引用来源可核对 ④ 评估集设**刁难题**（知识库里没有的问题）专项验证——我的系统对"公司食堂在哪"会老实回答"未找到"。

**Q6 SSE 和 WebSocket 有什么区别？前端怎么接流？**
SSE 单向（服务器→客户端）、基于 HTTP、可自动重连；WebSocket 双向、独立协议。LLM 输出是单方向推送，SSE 更简单够用。**前端有个坑**：原生 `EventSource` 只能 GET、不能带请求体，所以用 `fetch` + `ReadableStream` 手动读流，按空行切分 SSE 事件。

**Q7 Function Calling 的原理？模型会执行代码吗？**
**不会**。模型只做决策——输出 `tool_calls`（工具名 + 参数 JSON）；**执行是我的代码**，结果以 `ToolMessage`（带 `tool_call_id`）回填，模型据此给出最终答案，循环直到不再需要工具。`tool_call_id` 是为了在并行调用多个工具时把"请求"与"结果"配对。

**Q8 Agent 为什么要设循环上限和失败熔断？**
模型可能反复调用同一个失败工具（死循环、白烧 token）。**循环上限**兜住无限循环；**连续失败熔断**（连续 2 次 error）在给模型一次反思机会后强制终止，避免无谓消耗。

**Q9 为什么用 Milvus？换向量库要改多少代码？**
Chroma 是本地单文件库，适合开发；Milvus 支持高并发与分布式扩展，是生产首选。因为项目做了分层封装（`services/vector_store.py` 是唯一创建向量库的地方），**切换后端只改配置 + 这一个文件**——实测从 Chroma 切到 Milvus，`ingest` / `retriever` / `app` 一行未改，评估指标也保持一致（90% / 100%）。

**Q10 你怎么证明系统效果好？**
两个层面：① **评估集**：10 条（9 条知识问答 + 1 条防幻觉刁难题），量化"检索命中率 Recall@4"与"端到端准确率"，并在两种向量库上验证一致；② **单元测试**：pytest 覆盖判卷逻辑与工具纯逻辑（8 个用例，秒级反馈），防止改动引入回归。

## 四、亮点清单（主动讲，别等问）

1. **引用来源 + 防幻觉闭环**：回答可追溯，知识库没有的不编造
2. **评估驱动开发**：建评估集 → 发现判卷误判 → 调阈值 → 指标 20%→100%，全过程有记录（写进 README）
3. **双向量库后端**：Chroma / Milvus 配置切换，实测上层零改动、指标零变化
4. **生产级 Agent 设计**：循环上限 + 失败熔断 + 会话记忆 + 未知工具兜底
5. **RAG 即工具**：把检索封装成 Agent 工具，静态知识与私有动态数据统一入口
6. **工程化**：分层架构、配置驱动、Docker 三件套部署、pytest 单测、完整文档（架构 / API / 部署 / 评估）

## 五、追问应对与反问

**遇到不会的**：诚实说"这块我还没深入"，再转到相邻的、你会的部分。

**准备一个踩坑故事**（三选一，按"现象 → 排查 → 根因 → 解决"讲）：
- **环境/版本**：langchain-milvus 新版报 `should create connection first` → 读源码发现它的连接别名取自 pymilvus 客户端内部值 → 改用 `host`/`port` 预建立连接解决；同时把可用版本组合锁进依赖文件
- **路径问题**：相对路径导致向量库写到了别的目录、`.env` 读不到 → 根因是"相对路径跟着当前工作目录走" → 全部改为基于 `BASE_DIR` 的绝对路径
- **安全**：曾把 API Key 硬编码进代码 → 根因是 `.env` 加载路径失效 → 修为绝对路径加载 + 轮换密钥 + `.gitignore` 屏蔽
